# Non-functional requirements (NFRs) plan

These requirements describe the capstone demo, not a production service-level agreement. “Target” is the intended
acceptance criterion; “Status” distinguishes existing design or evidence from work that still needs proof. Record
release blockers and exceptions in the [risk register](risk-register.md), and link final evidence from the
[defense evidence index](../defense/evidence-index.md).

| Area | Target for the demo | Verification and evidence | Status |
| --- | --- | --- | --- |
| Security and authorization | The API is the security boundary. Protected endpoints reject missing, invalid and expired JWTs with 401; role-restricted endpoints reject unauthorized roles with 403. JWTs are signed and expire after 30 minutes. | Backend security tests and deployed smoke checks for anonymous 401 and wrong-role 403; review the filter chain against [ADR 0006](adrs/0006-use-self-issued-jwts-for-auth.md). | JWT design and tests are specified in ADR 0006; retain deployed smoke evidence. |
| Secrets and configuration | No passwords, signing keys, database credentials or deployment tokens are committed or printed in logs. Non-development environments fail to start if required configuration is absent; production secrets come from scoped environment secrets/Kubernetes Secrets. | CI secret scan; inspect deployment configuration and logs; verify startup with required configuration absent. | Secret handling is planned in the [environment strategy](environment-strategy.md); deployment proof remains tracked in the [risk register](risk-register.md). |
| Privacy and data handling | Use synthetic fixtures only. Do not put interaction summaries, customer names or emails in Kafka events; do not log free-text summaries. | Inspect event contract and emitted records, review logs, and confirm fixtures in local/CI/demo environments. | The event contract excludes summaries and customer PII; confirm implementation and deployment evidence. |
| Data integrity and durability | A successful write remains available after API restart. Invalid or unauthorized writes do not change data. Database commit is authoritative; Kafka publication occurs after commit and may fail without undoing the interaction. | API/UI persistence demo, database query after restart, negative-path tests, and Kafka failure test; document any publication failure behavior per [ADR 0005](adrs/0005-publish-events-after-commit.md). | Persistence and failure behavior have defined checks; deployed evidence and the known event-delivery gap remain release considerations. |
| Availability and recovery | No uptime guarantee is claimed for this instructional demo. The deployed API exposes liveness and readiness probes; a failed deployment can be rolled back to the previous image digest, followed by smoke checks. | Verify probe behavior, execute authenticated/denied-path smoke, roll back through the release process, and repeat smoke. Capture run links and image digests in the [CI/CD runbook](capstone-cicd-runbook.md). | Probe and rollback approach is planned; target-cluster proof is tracked in the [risk register](risk-register.md). |
| Performance | For the expected small, seeded capstone-demo workload, customer search, profile/timeline reads and interaction writes should complete within 2 seconds at the 95th percentile, excluding initial application startup. Customer search queries use an index scan, not a sequential scan. This is a demo target, not a capacity or production-load claim. | Measure representative requests against the seeded dataset before defense; record environment, sample size and results in the evidence index. Investigate any endpoint that misses the target. Run `EXPLAIN` on the search query against the seeded database and confirm an index scan. | No baseline or repeatable load measurement is recorded yet. |
| Accessibility and usability | Core workflows are usable by keyboard; controls have accessible names, focus is visible, validation and errors are understandable, and loading, empty and failure states are distinguishable. | Manually exercise login, search, profile and interaction workflows using keyboard only; inspect labels, focus order, errors and responsive layouts. Track follow-up work in the evidence index. | Plain CSS and semantic HTML are the chosen approach ([ADR 0004](adrs/0004-ui-library.md)); accessibility review evidence is pending. |
| Compatibility and responsive behavior | Support current stable Chrome and Edge for the demo, with the core workflow usable at desktop and narrow/mobile viewport widths. | Smoke the core workflow in both browsers and inspect the UI at representative desktop and narrow viewport sizes before defense. | Target; browser/viewport evidence is pending. |
| API compatibility | `/api/v1` stays stable: changes are additive only, and breaking changes go to `/api/v2`. | Review controller endpoints against [`contract.md`](contract.md) and its changelog for each API change. | Target; enforced by review of contract changes. |
| Maintainability and delivery | Changes pass the existing frontend production build and backend verification in CI. Deploy the exact image digest produced by CI; configuration varies by environment, not by rebuilding the artifact. | Required `frontend` and `backend` checks, image-manifest/digest evidence, and deployment runbook. | CI and digest workflow are documented in the [CI/CD runbook](capstone-cicd-runbook.md); deployment completion is tracked in the [risk register](risk-register.md). |
| Observability and supportability | Propagate `X-Correlation-ID` through API responses/logs and Kafka events so a request can be traced without exposing interaction text. Health probes remain available for the platform. | Submit a request with a known correlation ID and trace it through API logs and event evidence; verify health endpoints and ensure sensitive text is absent. | Correlation and health behavior are specified in the contract and architecture; end-to-end deployed evidence remains to be captured. |

## Scope and review

- These targets are for the capstone's synthetic-data demo. They do not establish production availability, security certification, or capacity for real customer traffic.
- Before the defense, replace pending status notes with links to evidence or document a specific exception and owner in the risk register.
- Revisit targets if deployment constraints, the demo workload, or the product scope materially changes.
