# Backend demo (Lab 49)

How to run the interaction slice locally and prove that `POST /api/v1/interactions` saves to PostgreSQL and publishes
a Kafka event that the consumer handles, plus the failure cases. Every output below is from a local run on 2026-10-12
at `59cc608`. The story and its acceptance criteria are [CAP-12](backlog.md#cap-12--record-a-customer-interaction).
The UI side is in [the frontend + persistence demo](frontend-persistence-demo.md).

## What the slice is

| Layer | What | Where |
| --- | --- | --- |
| API | `POST /api/v1/interactions` returns 201 with the saved interaction; `GET ?customerId=` lists the timeline | `InteractionController` |
| Service | One transaction: find the customer or 404, save, raise `CustomerInteractionRecordedV1` | `InteractionService` |
| Persistence | `customer_interaction` row, FK to `customer`, type checked by the database | `V1__crm_schema.sql` |
| Event | Published after commit to `crm.customer.interactions.v1`, keyed by customer ID ([ADR 0005](adrs/0005-publish-events-after-commit.md), [ADR 0003](adrs/0003-define-kafka-contract.md)) | `InteractionEventPublisher` |
| Consumer | Group `crm-interactions`; skips a duplicate `eventId`, retries twice, then the DLT | `InteractionEventConsumer`, `KafkaConsumerConfiguration` |
| Security | Bearer JWT from `POST /api/v1/auth/login`; no token is 401 ([ADR 0006](adrs/0006-use-self-issued-jwts-for-auth.md)) | `SecurityConfiguration` |
| Errors | RFC 9457 Problem Details with the request's correlation ID ([ADR 0002](adrs/0002-ids-and-errors.md)) | `ApiExceptionHandler` |
| Observability | `X-Correlation-ID` goes into the row, the event and every log line as `[correlationId=...]` | `CorrelationIdFilter` |

## Persistence

| Item | Value |
| --- | --- |
| Migrations | V1 `crm schema` to V5 `customer version`, all applied by Flyway at startup (`Successfully validated 5 migrations`) |
| Interaction key | `interaction_id uuid`, generated by the service |
| Customer key | `customer_id bigint` from a sequence internally; the public `CUS-1001` ID is unique and is the only one the API shows |
| Timeline index | `ix_interaction_customer_created (customer_id, created_at DESC)`: one customer's newest interactions first, no table scan |
| Profiles | `dev` and `test` both run against PostgreSQL 16 from `compose.yaml`. No H2. Kafka tests use an embedded broker, so CI needs no Kafka container |

## Run it

Needs Java 21, Docker and OpenSSL. From the repository root:

```bash
bash scripts/setup-local.sh
docker compose up -d
cd backend
./mvnw spring-boot:run
```

`setup-local.sh` creates `.env` and the JWT keys, both gitignored. Compose starts PostgreSQL, Kafka and a one-off job
that creates `crm.customer.interactions.v1` and its `.DLT`. The API is ready when
`curl localhost:8080/actuator/health/readiness` returns `{"status":"UP"}`.

## Happy path: `CUS-1001` with `lab-request-001`

Sign in as `agent1` with the password from `.env`, then record a call. Run from `backend/`:

```bash
set -a; . ../.env; set +a
TOKEN=$(curl -s localhost:8080/api/v1/auth/login -H 'Content-Type: application/json' \
  -d "{\"username\":\"agent1\",\"password\":\"$DEMO_AGENT_PASSWORD\"}" | sed -E 's/.*"accessToken":"([^"]+)".*/\1/')

curl -i localhost:8080/api/v1/interactions -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -H 'X-Correlation-ID: lab-request-001' \
  -d '{"customerId":"CUS-1001","interactionType":"CALL","summary":"Demo call: asked about statement dates"}'
```

```text
HTTP/1.1 201
{"id":"7852cf43-0ca3-4e87-bd51-834937c50b8a","customerId":"CUS-1001","interactionType":"CALL",
 "summary":"Demo call: asked about statement dates","correlationId":"lab-request-001",
 "createdAt":"2026-10-12T17:27:41.645085Z","version":0}
```

```bash
docker exec crm-postgres psql -U crm -d crm -c "select i.interaction_id, c.public_id, i.interaction_type, i.correlation_id from customer_interaction i join customer c using (customer_id) order by i.created_at desc limit 1;"
```

## Failure paths

| Request | Result | Row or event created? |
| --- | --- | --- |
| `CUS-9999` with `X-Correlation-ID: lab-request-002` | 404 `application/problem+json`, `"detail":"Customer CUS-9999 was not found"`, `"correlationId":"lab-request-002"` | No: 0 rows with `lab-request-002`, nothing on the topic |
| `"interactionType":"FAX"`, blank summary | 400 Problem Details, `"detail":"Invalid request"` | No |
| No `Authorization` header | 401 | No |

## Known limits

- Publish after commit, not an outbox ([ADR 0005](adrs/0005-publish-events-after-commit.md)): a 201 means the row
  is saved, not that the event was delivered. If Kafka stays down past the producer's two-minute delivery timeout,
  the event is lost with an error log and nothing resends it
  ([Kafka failure drills](../reports/kafka-failure-drills-2026-10-12.md)).
- A request with no header and no `correlationId` in the body gets `lab-request-001`. The UI always sends its own.
- Edits and deletes don't publish events.
- Demo accounts live in memory with no lockout or refresh tokens ([ADR 0006](adrs/0006-use-self-issued-jwts-for-auth.md)).
- The local stack is shared by every checkout on the machine, so the timeline will hold earlier test rows.
